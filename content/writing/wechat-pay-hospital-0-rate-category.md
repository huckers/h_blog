客户是一家公立医院，要收学生体检费。我在《入驻结算规则》里翻到一行：

**724，事业单位，费率 0%，适用行业「49 公立医院」。**

事业单位、公立医院、零手续费——三个词凑在一起，看着就是为这个场景准备的。我把零手续费写进了给院方的成本测算。

三天后我把那段测算删了。

## 条件写在表格的注里，不在费率上

那一行字后面还有一句注，我第一遍读表格时跳过了：

> 注：收款场景需为基础保障性诊疗场景，**不包含商业和消费医疗场景**，公立医疗场景定义详见……

后面链到《医疗行业场景定义及上传规范说明》。那份文档开篇给了三个定义：

| 类型 | 官方定义原文 |
|---|---|
| 基础保障性诊疗 | 目的在于治病救人，患者无法自主决策，一切都要遵医嘱进行，属于刚需治疗 |
| 消费医疗 | 由顾客主动做出选择，其目的在于预防或改善，**最为典型的对应为体检和医美**（包括齿科矫形等）业务 |
| 商业缴费 | 在公立医疗场景发生的与医疗无关的、商业性质的消费场景 |

「最为典型的对应为体检」。不是"体检可能算"，是"体检就是那个例子"。

同一份文档的场景值表里，`BODY_TEST` 的说明就一个字：体检。它被归在「商业场景-消费医疗」那一组下面。

## 我试过的最有说服力的反驳

这批体检不是家长自己挑的。它由政府、教育部门统一组织，面向升学，分派给医院和学校，不做就升不了学。

对照上面的定义，「患者无法自主决策」这一条是吻合的。我当时觉得这就是答案：它是刚需，它就属于基础保障性诊疗。

这条推理有两处挡不住。

**一是官方定义里没有这个例外。** 正文把体检整体列入消费医疗，没有为"指令性"留口子。审核执行时按字面类目判断，不按个案性质判断——个案性质需要人来读材料，而审核流水线上没有这一环。

**二是即使定性能成功，场景值表里也没有地方放它。** 诊疗场景只有五个：`REGISTRATION_FEE` 挂号、`MEDICINE_AND_TEST` 门诊缴费、`HOSPITALIZATION` 住院、`ONLINE_CONSULTATION` 在线问诊、`NUCLEIC_ACID_TEST` 核酸。没有一个能对应"政府统一组织的体检"。要传就只能传 `BODY_TEST`，那等于自己承认它是消费医疗。

这条论点我没有扔——它在申诉、在向院方解释"为什么费率不是 0"时是有用的。但它改变不了类目。

## 我原以为的，和实际的

| 我原以为 | 实际 |
|---|---|
| 0% 是给公立医院的优惠 | 0% 是一份带条件的准入承诺，条件就是「不用于消费医疗」 |
| 体检属于医疗，所以该在医疗类目下 | 体检在这些规则里的位置，写在「其他缴费」的资质说明里 |
| 类目选错，事后改一下就行 | 费率不跟着类目走，改类目可能只改了名字 |

第三条是读官方 Q&A 才注意到的：

> 签约后在【账户中心-商户信息-企业信息与经营信息】点「修改」，3~5 个工作日，**仅支持改类目和经营范围，费率与结算周期不变**。

也就是说，一个已经开通的 0% 商户号，可能被改成「其他缴费」而费率仍是 0%。这个组合比不改更麻烦：类目名看着对了，费率还是那个被明文排除体检的 0%。

判据只能有一条：**费率和类目必须同时变，只变一项等于没改。**

## 根因：我一直在看价码，没看承诺

把两份文档摆在一起，结构其实很简单。那张表有五列：

| 列 | 是什么 | 我的注意力 |
|---|---|---|
| 结算规则 ID（724 / 725） | 费率 + 入账周期 | 一直盯这列挑数字 |
| 适用行业 | 准入的业务范围 | 扫一眼 |
| 特殊资质 | 证明你能干这行的材料 | 需要时才看 |
| 注 | 这一行的**使用条件** | **完全跳过** |

决定"能不能收这笔钱"的是最后一列。费率是承诺的价码，承诺本身写在注和资质里。

更别扭的是，这张表是**审核侧视角**，按结算规则 ID 排列；而申请页是**产品视角**，按行业大类排列。724 和 725 在表里紧挨着，在申请页里隔了很远——725 下面那个行业叫「其他缴费」，它不在「医疗」大类下。

## 正确的位置：725 + 行业 40「其他缴费」

官方其实早就为体检准备好了位置，就写在 725 那一行：

> **725，事业单位，费率 0.6%，入账周期 T+1**
> 行业 40 其他缴费，特殊资质：必填
> 1、拍卖业务请提供《拍卖经营批准证书》
> 2、**如为公立医院消费医疗、商业缴费场景请提供《医疗机构执业许可证》**
> 3、其他业务请提供收费授权证明文件（如授权证明书或合同）

第 2 条那句"公立医院消费医疗、商业缴费场景"，就是给体检、医美、停车、食堂这类业务写的。而《医疗机构执业许可证》本来就在医院手里。

这里还有个坑：725 的「结算规则描述」写的是「提供网上交易场所或信息服务的业务、通讯业务、财经类业务及其他平台服务、餐饮、零售、交通出行等实体业务」——里面根本没有"缴费"两个字。按描述找会找不到，得按**行业名**找。

## 但界面上找不到它

2026-10-30 实测：申请页「医疗」大类下只有「公立医院」一个选项，没有「其他缴费」。

纸面上正确的路径，在界面上走不通。我是这样处理的：

1. 先看有没有独立的「结算规则 / 结算费率」栏——有些申请页把它和「所属行业」并列，那样最省事，直接在结算规则里挑 0.6% 那项；
2. 再去「生活服务 → 生活缴费 / 居民生活服务」找，或者在类目搜索框里搜「缴费」两个字；
3. 都没有，打 95017 让客服指定类目和结算规则，并且**要工单号**。

第 3 步不是兜底，是常规操作。平台侧口径本身就不完全一致，客服给的类目名可以直接用在申请单上。

## 怎么证明选对了

《入驻结算规则》页面顶部有一句话，也很容易跳过：

> 由于各个行业和商家的具体情况不尽相同，**不具有合同法律效力**，具体费率以商家在微信支付商户平台中的核准记录为准。

这句话把验收标准定死在了商户平台上。所以别凭"提交成功"的提示判断，去两个地方各看一遍：

| 位置 | 看什么 |
|---|---|
| 签约页 | 费率是不是 0.6% |
| 账户中心 → 商户信息 → 经营信息 | 类目名里有没有「缴费」，费率是不是 0.6% |

两处都对上才算改完。状态提示不等于核准记录。

## 连带的第二道题：如果留在医疗类目

如果这个号最终仍在医疗类目下（比如以后还要收挂号、门诊），还有一道题要做。

《医疗行业场景定义》要求下单时回传场景值：

> 商户在请求参数的 `goods_tag` 字段，根据对应订单的医疗场景值，按分类规范传入。

```json
{
  "description": "学生体检费",
  "out_trade_no": "T202610300001",
  "amount": { "total": 2000, "currency": "CNY" },
  "goods_tag": "BODY_TEST"
}
```

而 `goods_tag` 在通用《JSAPI 下单》文档里的定义是「订单优惠标记」，不是医疗场景字段。这不算文档打架——通用文档管字段的通用语义，行业规范管本行业的附加义务。行业规范还专门写了一条「确保此字段**未使用于其他用途**」，说明它清楚自己在借用这个字段。

两点提醒：

- 传什么都不会报错，因为它是自由字符串。**"传了不报错"证明不了任何事**，别拿它验证字段用途；
- 别为了让订单看起来不像体检而去改 `description`。支付页、账单、商户平台三处都显示它，而公立医院的入驻说明函里明写了不得造假场景。

对 0% 类目来说这道题无解：传 `BODY_TEST` 是如实自证消费医疗，不传是没履约。所以真正的修法还是前面那件事——换类目。

## 一句话

**费率不是一个可选的价格，它是一份准入承诺的摘要。选类目时先读承诺，再读价格。**

往前延伸一步：任何"给你免手续费"的资格，都要先问条件。平台不平白让利，让利的那部分总是用某个范围限制换来的——而范围限制通常不印在价目表上，印在价目表的注里。
