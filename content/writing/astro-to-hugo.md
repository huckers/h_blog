设计稿先定的。十一张页面、一套 1px 线条的排版系统、1440 栅格，全部画完才考虑用什么渲染。这个顺序其实是对的——先决定长什么样，再决定谁来生成它。

选渲染引擎的时候我给自己列了三条硬约束：

1. Markdown 是唯一输入源，不经过 Web 后台，不进数据库；
2. 写完落盘就该发布，不需要再点一次按钮；
3. 视觉不能被现成主题绑住。

按这三条筛，剩下 Astro 和 Hugo。

## 我最初的判断是错的

当时我选 Astro，理由是 content collections 有 schema 校验。我写 frontmatter 偶尔会漏字段，Astro 会在构建时直接报错，Hugo 不会。

这个理由本身没错，但它推导出的结论错了——**我为了一个可以花三十行脚本解决的问题，选了整套更重的工具链。**

更重要的是，我给 Astro 的另一个加分项是错的。我当时想：Astro 构建 5 秒，Hugo 0.1 秒，差 50 倍，当然是 Hugo 快，但 5 秒也能忍。

我把比较的对象搞错了。真正的时间不在 `build`，在它前面：

| 环节 | Astro | Hugo |
|---|---|---|
| 安装依赖 | `npm install`，20~40 秒 | 无 |
| 构建 | 5 秒左右（含代码高亮） | 0.1 秒出头 |
| 产物 | `dist/` | `public/` |
| 部署总耗时 | 约 30~50 秒 | 约 3~8 秒 |

Cloudflare Pages 每次部署都从干净环境开始，`npm install` 那一段躲不掉。所以差距不是 50 倍，是 5~10 倍的**总等待时间**——而这段时间正好卡在"我写完想马上看到线上效果"的那一刻。

至于 Go Template 难改这件事，我一开始把它算成 Hugo 的劣势。但模板一共就写一次、改几十次，而且改模板的活儿本来就是交给工具做的，不是我自己一行行敲。**这个成本被我高估了。**

## 重新排一遍权重

| 维度 | Astro | Hugo | 谁赢 |
|---|---|---|---|
| 部署总耗时 | 30~50s | 3~8s | Hugo |
| frontmatter 校验 | schema 内建 | 无，要自己写 | Astro |
| tags / series / 归档 | 手写聚合逻辑 | taxonomies 内建 | Hugo |
| 模板出错时的反馈 | TypeScript 报错 | 静默渲染空白 | Astro |
| 依赖体积 | node_modules 上千个包 | 一个二进制 | Hugo |
| Markdown 里插组件 | MDX 支持 | shortcode，够用 | 平手 |

我原来只盯着第三行和第四行，忽略了第一行和第三行的另一半。**"tags / series / 归档"这件事，Hugo 是完全内建的**——我只要在 `hugo.toml` 里声明，`/tags/`、`/series/` 这些页面自动就有，连聚合逻辑都不用写。在 Astro 里这些全是我手写的 `getCollection` 加 `reduce`。

## 但有一件事必须补上

Hugo 唯一的实质性劣势是第四行：**模板里写错字段名，它不报错。**

`.Params.tgas` 拼错了，Hugo 不吭声，那一格就是空白。页面能打开、能上线，你可能几个月后才发现某个模块一直是空的。Astro 那边是 TypeScript，同样的错误在构建时就红了。

这个缺口我用一个校验脚本补上，不引任何依赖，`hugo` 之前跑一次。它只做一件事：把"能上线但不正确"的状态，改成"不能上线"。花三十行代码，换掉整套 schema 体系——这笔账是划算的。

> 选型的错误很少出在"你看错了某个工具的优点"，多半出在"你给某个优点的权重，建立在一个没验证的前提上"。我当时的前提是"构建时间就是那 5 秒"，而它其实是 50 秒。
