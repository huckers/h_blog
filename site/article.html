把 CMS 做成多站点：
一次 schema 设计的取舍

Date2026-10-27
Read14 min
Words3,240
TopicBackend

四端共用一套内容模型之后，我发现真正决定后期成本的，不是表怎么建， 而是「哪些字段允许各站点自己改」这条边界画在哪儿。

01先说结论

单库多站点、多库单实例、多库多实例，三种切法我都试过。最后落在 单库 + 站点维度表上，理由是它把「跨站点检索」这件迟早要做的事， 变成了一次普通的 JOIN，而不是一次数据迁移。

代价也明确：所有表都要带 site_id，所有查询都要自己记得加条件。 这不是免费的，只是它比「先分库、以后再想办法聚合」便宜。

多站点的核心矛盾从来不是隔离，而是共享。
隔离有现成方案，共享没有。

02三种切法

先看对比。这张表是当时贴在白板上、被反复擦掉的版本，最后留下来的是第三列。

第二列「隔离度」看起来最重要，实际上最先被排除。因为四个站点共享的是同一批作者、 同一套标签体系，隔离做得越彻底，这部分冗余就越多。

站点表只放三件事

我一开始想做一个「站点配置中心」，能覆盖主题色、导航、SEO、甚至模板。 做到第三周就发现，配置项一旦超过二十个，它本身就成了一个需要文档的子系统。 于是砍到只剩三件事：

  • 身份：域名、站点名、默认语言
  • 继承：哪些字段允许覆盖，用一张 site_field_override 描述
  • 开关：功能级灰度，只允许布尔值，不允许值配置
sqlschema/site.sql
-- 站点只描述「能改什么」，不描述「改成什么」
CREATE TABLE site (
  id            BIGINT PRIMARY KEY,
  host          VARCHAR(128) NOT NULL UNIQUE,
  name          VARCHAR(64)  NOT NULL,
  locale        CHAR(5)      NOT NULL DEFAULT 'zh-CN'
);

-- 覆盖关系单独一张表，避免 site 表长成 40 列
CREATE TABLE site_field_override (
  site_id       BIGINT NOT NULL,
  entity        VARCHAR(32) NOT NULL,  -- post / page / nav
  field         VARCHAR(32) NOT NULL,
  PRIMARY KEY (site_id, entity, field)
);

03真正贵的不是表结构

改表结构花了两天。让它跑对花了三周。问题全部出在「忘记加 site_id」上， 而且这类 bug 有个恶劣的性质：它不会报错，只会安静地多返回几条别的站点的数据。

我最后用了一个很土的办法：在 DAO 层做一个只有 site_id 一个参数的 ScopedQuery 包装，所有跨站点查询必须显式走 unscoped()。 于是「漏加」从静默通过变成了一个需要写出来的动作。

这类改法的价值不在于防错，而在于把错误变成可见的决策。 代码评审时看到 unscoped()，人自然会问一句「这里为什么可以跨站点」。

04落地顺序

如果重来一次，我会按这个顺序做，而不是先设计表：

  1. 先把「跨站点检索」的查询写出来，它能暴露出所有模型上的错误假设
  2. 再定覆盖边界，只允许字段级覆盖，不允许结构级
  3. 最后才建表、写迁移

先有查询，后有结构，这个顺序在数据建模上几乎总是对的。因为查询是你真正要跑的东西， 而结构只是为了让查询跑得动。

Notes — 本文基于一个多站点 CMS 的真实重构过程，表结构与代码已做简化。
